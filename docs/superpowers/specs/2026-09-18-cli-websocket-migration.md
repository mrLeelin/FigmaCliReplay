# CLI + WebSocket 全链路迁移规格

状态：设计访谈产物，架构及运行规则已获用户确认；下述实现约束与验收清单用于后续实施，尚未证明已实现。

## 目标与边界

移除本项目 MCP 方案，以项目 CLI 提供用户和 AI 可调用的统一入口。常驻 Relay 协调任务；CLI、Figma 插件、Unity Bridge 的业务命令、状态与进度均使用 WebSocket。HTTP 仅保留文件下载和 WebSocket 升级所需处理，不保留业务轮询或 MCP 兼容执行通道。

保留现有设计整理、PSD 导入、Figma 与 Prefab 双向导入、图片处理和 AI 能力。Codex、Claude 等 AI CLI 继续承担模型执行。更换传输不改变现有确认、写入授权、回滚、资源访问控制与多目标选择边界。

## 已确认的行为

1. Relay 使用独立启动入口；业务 CLI 不自动启动、重启或停止服务。
2. CLI 断开不等于任务取消。提交成功后可用任务 ID 重新查询、订阅或明确取消。
3. Figma、Unity 断开后等待重连。写操作结果未知时先核对执行状态，不自动重放。
4. 各端同步升级，一次切换；旧端获得升级提示，不继续执行业务。
5. 图片等大文件通过受控 HTTP 下载，文件相关命令与下载凭据通过 WebSocket 交换。

## 实现约束

这些是基于已确认行为制定的工程约束；具体命令名、字段布局与超时值在实现时结合现有代码确定。

- 项目 CLI 提供帮助、结构化 JSON 输出、明确退出码；诊断日志写 stderr，避免污染机器可读结果。
- 长任务支持提交、查询、等待或订阅、取消。提交返回稳定任务 ID；请求关联字段复用现有 operationId、requestId、runId 等概念，明确映射关系。
- CLI 使用明确目标标识。只有一个可选目标时允许省略；多个 Figma 会话或 Unity 项目存在歧义时拒绝猜测。任务开始后冻结目标。
- Relay 是任务状态的权威来源。客户端连接、执行端连接与任务生命周期分别管理；取消请求不能直接伪造已取消终态。
- 将接收确认与执行完成区分。请求去重不能只依赖当前 socket；重复提交应返回已有任务或明确冲突。
- 已执行但未回传结果的写操作进入待核对状态。无法核实时明确报告结果未知，不能报告成功、当作未执行，或悄悄重试。
- 重连等待必须有边界；执行端永久离线时返回可诊断状态。Relay 重启不得使不确定写入被自动重复执行。任务保留期限与恢复范围须在实现规格中明确并测试，不能宣称无限期持久化。
- 握手识别角色、协议版本与目标身份；保留本机访问限制和会话授权。客户端不得通过伪造角色绕过写入闸门。
- 保留 operationId 贯穿的 started、progress、succeeded、failed、cancelled 日志以及拒绝、去重、重连、核对与回滚日志。
- 产品发布版本与消息协议版本分别管理。旧端拒绝应由最小版本诊断完成，不实现旧 MCP 工具调用。

## 验收

- 逐项映射全部旧 MCP 工具与业务 HTTP 路由，证明能力有新入口或已有明确废弃依据。
- 打通真实 CLI → Relay → Figma 的查询、修改与结果返回；打通 Unity 导入及失败返回。
- 提交后退出 CLI，重开 CLI 能定位同一任务；明确取消后查询到真实终态。
- 覆盖提交前断线、接收后断线、修改后结果回传前断线、重连与永久离线；写入不因重试重复发生。
- 多 Figma 会话、多 Unity 项目下不误选目标；旧版本获得可理解的升级提示。
- 文件下载仍受路径与访问控制约束；日志成功、失败和拒绝链可按 operationId 查询。
- 检查运行时 MCP SDK、入口、配置脚本、提示词及调用方残留；历史决策说明中的 MCP 字样不算运行依赖。
- 从干净安装与发布包验证 CLI 和 WebSocket 可用，确保启动、诊断、smoke 与打包脚本不会重新配置或启动 MCP；统一旧 skills 中与服务生命周期约束冲突的指令。
- 运行定向 Node/Python 测试、TypeScript 检查、完整构建、Unity 编译及真实跨端验证。静态检查不能代替运行验收。
